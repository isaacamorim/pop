# 📘 Documentação do Sistema de POP (Procedimento Operacional Padrão)

Esta documentação descreve o **modelo de dados**, **conceitos**, **regras de negócio** e **fluxo de uso** do sistema de POP integrado ao ambiente industrial (PCP / Chão de Fábrica).

O objetivo do sistema é:

* Padronizar instruções operacionais
* Integrar POPs ao apontamento de produção
* Permitir rastreabilidade, evidências e histórico
* Suportar uso em **desktop** e **celular**

---

## 🧠 Conceitos Fundamentais

### O que é um POP?

Um POP (Procedimento Operacional Padrão) é um conjunto estruturado de instruções que orienta o operador na execução correta de uma atividade, garantindo **qualidade**, **segurança** e **padronização**.

No sistema, o POP é tratado como:

* Um **template** genérico
* Com **versões** versionadas
* Aplicado a um contexto específico (NP, peça, operação, máquina, serviço)

---

## 🧱 Visão Geral do Modelo

O modelo foi dividido em **8 blocos principais**:

1. Templates (estrutura lógica do POP)
2. Versions (conteúdo versionado)
3. Steps (checklist / passos)
4. Attachments (anexos)
5. Links (amarração com NP / peça / operação)
6. Instances (execução real)
7. Instance Steps (evidências)
8. History (auditoria)

Essa separação garante:

* Reutilização
* Versionamento seguro
* Histórico completo
* Baixo acoplamento com o ERP

---

## 1️⃣ pop_template — Template de POP

Representa o **conceito base** do POP, sem conteúdo operacional detalhado.

```sql
CREATE TABLE pop_template (
  id BIGSERIAL PRIMARY KEY,
  code VARCHAR(50) UNIQUE,
  title TEXT NOT NULL,
  type VARCHAR(20) NOT NULL,      -- 'peca','operacao','maquina','servico'
  description TEXT,
  default_duration_seconds INTEGER,
  created_by INTEGER,
  created_at TIMESTAMP DEFAULT now(),
  active BOOLEAN DEFAULT true
);
```

### Tipos de Template (`type`)

* `peca` → POP ligado à peça
* `operacao` → POP ligado à operação da NP
* `maquina` → POP de uso/manutenção de máquina
* `servico` → POP genérico (embalar, limpar, organizar, etc)

📌 **Regra:** um template pode ter várias versões.

---

## 2️⃣ pop_version — Versão do POP

Contém o **conteúdo real** do POP.

```sql
CREATE TABLE pop_version (
  id BIGSERIAL PRIMARY KEY,
  template_id BIGINT REFERENCES pop_template(id) ON DELETE CASCADE,
  version_number INTEGER NOT NULL,
  summary TEXT,
  content TEXT,
  cod_tarefa VARCHAR(50),
  cod_maquina VARCHAR(50),
  is_standard BOOLEAN DEFAULT true,
  created_by INTEGER,
  created_at TIMESTAMP DEFAULT now(),
  active BOOLEAN DEFAULT true
);
```

### Pontos importantes

* Versionamento explícito (`version_number`)
* Apenas **uma versão ativa por template**
* `content` suporta **Markdown ou HTML**

📌 **Regra:** alterações criam **nova versão**, nunca sobrescrevem.

---

## 3️⃣ pop_step — Passos do POP

Permite estruturar o POP como **checklist sequencial**.

```sql
CREATE TABLE pop_step (
  id BIGSERIAL PRIMARY KEY,
  version_id BIGINT REFERENCES pop_version(id) ON DELETE CASCADE,
  seq INTEGER NOT NULL,
  title TEXT,
  instruction TEXT,
  requires_photo BOOLEAN DEFAULT false,
  requires_signature BOOLEAN DEFAULT false
);
```

### Uso prático

* Execução guiada
* Validação por foto/assinatura
* Ideal para celular no chão de fábrica

---

## 4️⃣ pop_attachment — Anexos

Armazena imagens, PDFs, diagramas, vídeos, etc.

```sql
CREATE TABLE pop_attachment (
  id BIGSERIAL PRIMARY KEY,
  version_id BIGINT REFERENCES pop_version(id) ON DELETE CASCADE,
  filename TEXT,
  mime VARCHAR(100),
  storage_path TEXT,
  uploaded_by INTEGER,
  uploaded_at TIMESTAMP DEFAULT now()
);
```

📌 **Regra:** anexos pertencem à versão do POP.

---

## 5️⃣ pop_link — Amarração com ERP / NP

Define **onde** o POP se aplica.

```sql
CREATE TABLE pop_link (
  id BIGSERIAL PRIMARY KEY,
  version_id BIGINT REFERENCES pop_version(id) ON DELETE CASCADE,
  link_type VARCHAR(20) NOT NULL,
  np_codigo VARCHAR(50),
  product_code VARCHAR(50),
  seq_cod VARCHAR(50),
  cod_tarefa VARCHAR(50),
  cod_maquina VARCHAR(50),
  tmp_maquina DECIMAL,
  tmp_setup DECIMAL,
  prod_por_hora DECIMAL,
  notes TEXT,
  created_at TIMESTAMP DEFAULT now()
);
```

### Tipos de Link (`link_type`)

* `np` → NP específica
* `peca_op` → Peça + operação
* `peca` → Peça genérica
* `maquina` → Máquina
* `tarefa` → Tarefa padrão
* `template_copy` → Cópia de outro POP

📌 **Regra:** um POP pode ter múltiplos links.

---

## 6️⃣ pop_instance — Execução do POP

Representa a **execução real** durante a produção.

```sql
CREATE TABLE pop_instance (
  id BIGSERIAL PRIMARY KEY,
  version_id BIGINT REFERENCES pop_version(id),
  pop_link_id BIGINT REFERENCES pop_link(id),
  started_at TIMESTAMP DEFAULT now(),
  finished_at TIMESTAMP,
  operator_id INTEGER,
  status VARCHAR(20),
  notes TEXT
);
```

### Status possíveis

* `started`
* `paused`
* `completed`
* `aborted`

---

## 7️⃣ pop_instance_step — Evidências

Guarda o resultado de cada passo executado.

```sql
CREATE TABLE pop_instance_step (
  id BIGSERIAL PRIMARY KEY,
  instance_id BIGINT REFERENCES pop_instance(id) ON DELETE CASCADE,
  step_id BIGINT REFERENCES pop_step(id),
  done BOOLEAN DEFAULT false,
  note TEXT,
  photo_path TEXT,
  recorded_at TIMESTAMP DEFAULT now()
);
```

📌 **Valor chave:** rastreabilidade e auditoria.

---

## 8️⃣ pop_history — Histórico e Auditoria

Registra **todas as ações relevantes**.

```sql
CREATE TABLE pop_history (
  id BIGSERIAL PRIMARY KEY,
  entity_type VARCHAR(30),
  entity_id BIGINT,
  action VARCHAR(40),
  user_id INTEGER,
  payload JSONB,
  created_at TIMESTAMP DEFAULT now()
);
```

### Exemplos de ações

* `create_template`
* `new_version`
* `link_created`
* `instance_completed`

---

## 🔁 Fluxo de Uso Resumido

1. Criar **Template**
2. Criar **Versão** do POP
3. Definir **Steps** e **Anexos**
4. Criar **Link** com NP / peça / máquina
5. Operador inicia **Instance**
6. Executa passos e registra evidências
7. Finaliza execução
8. Histórico é registrado

---

## 📱 Considerações de Interface

* **Cadastro**: celular (rápido e simples)
* **Execução**: celular ou desktop
* **Consulta / gestão**: desktop

✔ Integração com ERP sem acoplamento
✔ Auditoria completa
✔ Escalável para novas áreas

## 🚀 Próximos Passos Definidos (Decisões Atuais)

Com base nas decisões atuais, os próximos passos ficam definidos da seguinte forma:

### 1️⃣ Usuários e Acessos

* **Não haverá controle de permissões neste momento**
* Todos os usuários terão perfil único de cadastro
* Controle de acesso e perfis ficam planejados para uma **fase futura**

📌 *Motivo:* reduzir complexidade inicial e acelerar a entrega do MVP.

---

### 2️⃣ Campos Obrigatórios

* **Nenhum campo será obrigatório inicialmente**, além do mínimo técnico (PKs e FKs)
* Validações rígidas serão adicionadas conforme o uso real do sistema

📌 *Motivo:* permitir flexibilidade e adaptação ao processo real de fábrica.

---

### 3️⃣ Integração com Apontamento

* O sistema de POP **não será acoplado agora** à tela de apontamento
* A arquitetura já está preparada para que:

  * A tela de apontamento consulte POPs ativos
  * O operador visualize o POP durante o apontamento

📌 *Motivo:* garantir que o cadastro esteja sólido antes da integração operacional.

---

### 4️⃣ Versão Base do Modelo

* A **última versão do modelo enviada** foi aprovada como base oficial
* Ajustes futuros devem preservar:

  * Versionamento
  * Histórico
  * Desacoplamento do ERP

## 🧩 Arquitetura Inicial do Projeto

### 🔹 Opção A — Frontend e Backend Separados (Escolhida)

Nesta opção, o **backend (Flask)** funciona exclusivamente como **API**, e o **frontend** é uma aplicação separada consumindo essa API.

**Vantagens:**

* Melhor organização
* Facilidade de evolução do frontend
* Possibilidade futura de trocar tecnologia do front
* Reuso da API (desktop, celular, apontamento)

---
